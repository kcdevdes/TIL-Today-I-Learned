### 문제 1. 설비 테이블 설계하기 (기초 · DDL)
배터리 제조 공장에서는 여러 생산 설비를 관리하고 있다.
각 설비의 ID, 이름, 공정, 현재 상태를 저장하기 위한 `equipment` 테이블을 만든다.

**요구사항**
- `equipment_id`: 정수형 Primary Key, 자동 증가
- `equipment_name`: 최대 100자, NULL 허용하지 않음
- `process_type`: 최대 50자, NULL 허용하지 않음
- `status`: `RUNNING`, `IDLE`, `DOWN` 중 하나만 허용
- `created_at`: 설비 등록 시각, 기본값은 현재 시각

**입력 데이터**

| equipment_name | process_type | status |
| --- | --- | --- |
| Mixer-01 | Mixing | RUNNING |
| Coater-01 | Coating | IDLE |
| Press-01 | Pressing | DOWN |

**완료 기준**
- 테이블을 직접 만들고 데이터를 입력한 다음, `SELECT * FROM equipment;` 실행 시 세 행이 조회되어야 한다.

**핵심 개념**: `CREATE TABLE`, `PRIMARY KEY`, `NOT NULL`, `CHECK`, `DEFAULT`, `INSERT`

### 문제 2. LOT와 설비 연결하기 (중급 · 관계형 모델링)
하나의 LOT는 생산 과정에서 여러 설비를 통과할 수 있고, 한 설비도 여러 LOT를 처리할 수 있다.
따라서 LOT가 어떤 설비를 언제 통과했는지 기록해야 한다.

**요구사항**

`lot` 테이블
- `lot_id`: 자동 증가 Primary Key
- `lot_number`: 중복 불가능한 문자열
- `created_at`: 생성 시각

`process_history` 테이블
- `history_id`: 자동 증가 Primary Key
- `lot_id`: `lot` 테이블을 참조
- `equipment_id`: `equipment` 테이블을 참조
- `processed_at`: 처리 시각

**목표 데이터 관계**
- (원본 문제의 데이터 관계 내용이 누락됨 — 테스트 데이터는 직접 구성)

**과제**
- 데이터를 입력한 뒤, LOT 번호 `LOT-001`이 통과한 모든 설비의 이름과 처리 시각을 **오래된 순서대로** 조회하는 SQL을 작성한다.

**핵심 개념**: `FOREIGN KEY`, `UNIQUE`, `INSERT`, `INNER JOIN`, `ORDER BY`

### 문제 3. 설비별 생산 이력 분석 (도전 · 집계 SQL)
공정 엔지니어가 생산 이력을 분석하려고 한다.
문제 2에서 만든 `process_history`를 사용해서, 각 설비가 처리한 이력 건수를 조회한다.

**요구사항**
- 설비 이름과 처리 건수를 보여줄 것
- 처리 이력이 없는 설비도 결과에 포함할 것
- 처리 건수가 많은 설비부터 정렬할 것
- 처리 건수가 같다면 설비 이름 오름차순으로 정렬할 것

**원하는 결과 형식** (숫자는 예시, 테스트 데이터에 따라 달라짐)

| equipment_name | total_processed |
| --- | --- |
| Mixer-01 | 5 |
| Coater-01 | 3 |
| Press-01 | 0 |

- 핵심: `Press-01`처럼 처리 이력이 없는 설비를 결과에서 빠뜨리지 않는 것.

**핵심 개념**: `LEFT JOIN`, `GROUP BY`, `COUNT`, `ORDER BY`

### Key Concepts
- DDL objects persist in the DB → a script must be **re-runnable** (`DROP ... IF EXISTS` at the top).
- Drop order follows dependencies: child first (`process_history` → `lot` → `equipment` → type).
- `BIGSERIAL` vs `GENERATED ALWAYS AS IDENTITY` (SQL standard, blocks manual id insert).
- `DATE` loses time → use `TIMESTAMPTZ` for event times.
- `NOW()` = transaction start time, `clock_timestamp()` = actual call time.
- `UNIQUE` on `lot_number` protects traceability (no duplicate LOT numbers).
- `processed_at` (when the equipment processed) ≠ DB insert time → `NOT NULL` without default, so missing data fails loudly.
- In `FROM`/`JOIN`, each table appears once (use aliases); don't mix `FROM a, b` (CROSS JOIN) with `JOIN`.

### Mistakes and Fixes
| Mistake | Symptom | Fix |
| --- | --- | --- |
| Re-ran `CREATE TYPE` | `type "running_status" already exists` | `DROP ... IF EXISTS` at the top |
| Trailing comma after last column (twice) | `syntax error at or near ")"` | Remove the comma |
| Typo in `DROP TABLE IF EXISTS equipments` | Silently skipped, then `DROP TYPE` failed | `IF EXISTS` hides typos → always test by running twice |
| Leftover pasted text `INSERT INTO equipment ()` | Syntax error | Remove it |
| Same table listed 3 times in `FROM`/`JOIN` | `table name "equipment" specified more than once` | One `FROM` + one `JOIN` per table, with aliases |

- Reading errors: `LINE n` is relative to the statement start, and the real cause is often just before the reported token.
